# E02 capability options — decision pending

**Status:** Research for `aerio-c1x.5`, not an accepted architecture decision.
The owner chose a **TV-only product without an additional server**. The E01
reference behavior is in [platform decisions](platform-decisions.md). No
Simulator/retail TV result has yet been supplied for sync, discovery, PiP or
home integration; approval waits for E02.1/E02.2/E02.4 and product review.

| Capability | Evidence and technically distinct paths | Current decision gate |
| --- | --- | --- |
| Local-only usage | Packaged webOS app can have local data once persistence has been verified. E01 requires onboarding to work without a cloud account. | Keep standalone configuration usable regardless of later sync choice; verify on TV after storage/relaunch tests. |
| Apple iCloud KVS sync | Apple's pinned `Shared/SyncManager.swift` uses Apple-platform iCloud KVS and Keychain; no compatible webOS API is identified in LG's [public references](https://webostv.developer.lge.com/develop/references). Direct cross-device KVS access must not be claimed from a web view. | A TV-only app cannot simply reuse the Apple implementation. Explicit PO decision needed for an alternative import/transport if cross-Apple sync is required. |
| Google Drive AppData sync | Google's [TV/device OAuth flow](https://developers.google.com/identity/protocols/oauth2/limited-input-device) explicitly permits `https://www.googleapis.com/auth/drive.appdata`: TV displays a code, user authorizes in a browser on another device, TV polls for an access/refresh token. [Drive AppData](https://developers.google.com/drive/api/guides/appdata) is private to the registered app; Android's pinned `core/sync/` uses Drive AppData. Distinct TV OAuth client registration, token protection and Drive schema compatibility still need proof. | Candidate without a new AerioTV server. Do not promise Android interoperability merely because both use Drive: verify client/app-data ownership, actual snapshots and authorization configuration. Never ship an OAuth client secret in a package as a meaningful secret. |
| Secure token storage | LG [Keymanager3](https://webostv.developer.lge.com/develop/references/keymanager3) supports TEE-backed crypto **from webOS TV 24**, not the webOS 22 baseline. [LG submission guidance](https://webostv.developer.lge.com/distribute/app-self-checklist) requires careful credential storage. The bundled JS service has an app jail but that alone does not prove token secrecy at rest or backup/restore behavior. | Test feasible per-device credential handling on webOS 22; do not make Google sign-in a prerequisite for source setup. Record any minimum-version difference before approving Drive sync. |
| LAN companion remote | Android pinned [`CompanionProtocol.kt`](https://github.com/jonzey231/AerioTV-Android/blob/de9389f2661d3e2b142c10f5b9595213468c1bfb/app/src/main/java/com/aeriotv/android/core/cast/companion/CompanionProtocol.kt) uses `_aeriotv._tcp.` mDNS TXT `v`/`id`, WebSocket `/remote`, `hello` → `auth` (six-digit code or remembered token) → `authOk` then CastControl `cmd` messages. Its [TV host](https://github.com/jonzey231/AerioTV-Android/blob/de9389f2661d3e2b142c10f5b9595213468c1bfb/app/src/main/java/com/aeriotv/android/core/cast/companion/CompanionHostController.kt) advertises only while foreground and bounds pairing attempts. webOS bundled JS services have [network access](https://webostv.developer.lge.com/develop/guides/js-service-basics) but short lifetimes; Node 12 pure-JS WebSocket/mDNS support, multicast delivery and mobile-client discovery require demonstration on a TV. | Candidate entirely on-device; prove discovery **and** paired control on the target TV with an existing mobile client. A working loopback HTTP probe does not establish multicast or foreground service survivability. |
| Google Cast/AirPlay receiver | LG's system-level cast/airplay support and Android's proprietary Cast Connect SDK do not by themselves route an AerioTV sender into this webOS app. | No native receiver claim until an existing sender discovers/pairs and sends a channel into the app; keep companion-LAN exploration separate from proprietary Cast receiver assertions. |
| Picture-in-picture / home shelf | tvOS Top Shelf extension is Apple-specific. LG's [Home Screen](https://webostv.developer.lge.com/develop/guides/home-screen) and [Application Manager](https://webostv.developer.lge.com/develop/references/application-manager) document launcher metadata and relaunch parameters, not a verified AerioTV content-row extension or an OS-wide PiP contract. A resized **in-app** one-video mini-player is a distinct feature. | Probe fullscreen-to-corner video and lifecycle on TV. Do not advertise OS PiP or Top Shelf-equivalent integration without a documented permitted API and device proof. |
| Store deployment | A packaged app is required by the TV-only choice; [ACG rules](https://webostv.developer.lge.com/develop/guides/acg-guide) change across versions, and LG's [self-checklist](https://webostv.developer.lge.com/distribute/app-self-checklist) requires cursor/D-pad focus and playback controls. | E12 verifies actual app UX, artifacts, source notices, credentials and Store review; a successful developer IPK alone does not establish Store acceptance. |

## Decision sequence

First record the retail TV model, firmware/webOS version and E02.1/E02.2/E02.4
probe outcomes in [the evidence ledger](webos-feasibility.md). Then establish
which of the options above has a documented, testable implementation on webOS
22+. Present proven options and any genuine parity gap for explicit PO
acceptance; write an ADR for the chosen design. No separate hosted AerioTV
service is permitted by the current product decision. Multiview remains
deferred and is not part of this decision sequence.
